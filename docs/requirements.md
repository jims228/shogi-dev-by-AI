> ステータス: **叩き台 / レビュー待ち**
> 作成日: 2026-03-23
> 開発方式: **2日完成 + 品質ゲート**（DEC-008）

## プロダクトの核

**将棋の局面・棋譜・変化を、初心者〜中級者にも分かる形で説明するAI。**

これはニュースアプリでも学習ドリルでもない。
「将棋を言語化する能力」そのものがプロダクトである。

### v2（shogi-commentary-ai）との関係

- **v2は参考アーキテクチャとしてのみ使用する**
- コードのコピー・流用は行わない（clean-room implementation）
- フロントエンドもバックエンドも完全新規実装
- 参考にするもの: 責務分割、API設計パターン、評価観点
- 詳細: `docs/architecture-principles.md` を参照

入力: 局面（SFEN）、棋譜（KIF/CSA）、指し手の変化
出力: その局面で「何が起きているか」「なぜその手か」「他の手との違い」を平易な日本語で説明

---

## 1. ターゲットユーザー

| 属性 | 内容 |
|------|------|
| 棋力（MVP） | **初心者（将棋ウォーズ5級〜3級前後）** |
| 棋力（MVP後） | 中級者（将棋ウォーズ2級〜2段程度）は後回し |
| ペルソナ | 「手は読めないが、何が起きているか知りたい」人 |
| 利用シーン | 自分の対局の振り返り、プロ対局の観戦、棋譜並べ中の疑問解消 |
| 局面入力（MVP） | **ユーザーが手動でSFEN/KIFをテキスト貼り付け** |

---

## 2. ユーザー課題

1. **「なぜその手か」が分からない**
   - 評価値+300→-200に動いた。でもなぜ？が分からない
   - 解説書は有段者前提で、噛み砕かれていない

2. **変化の比較ができない**
   - 「▲7七角ではなく▲5五角の方がいい」と言われても、違いが分からない
   - 自分で変化を読む力がまだないので、言語で教えてほしい

3. **局面の方針が立てられない**
   - 「ここからどう指せばいいの？」に答えてくれるツールがない
   - 将棋エンジンは最善手を出すが、方針は教えてくれない

---

## 3. 提供価値

> **将棋の「なぜ」を、あなたのレベルで言語化する。**

| 価値 | 内容 |
|------|------|
| 局面解説 | 「今この局面で何が起きているか」を説明 |
| 手の理由 | 「なぜこの手が良いか / 悪いか」を根拠付きで説明 |
| 変化の比較 | 「A手とB手で何が変わるか」を対比して説明 |
| 方針の提示 | 「ここからの大まかな方向性」を示す |
| レベル適応 | 初心者→比喩多め / 中級者→具体手順で説明 |

---

## 4. コアループ

```
局面/棋譜を入力
    ↓
AIが局面を解析し、平易な日本語で解説
    ↓
ユーザーが質問（「なぜ？」「他の手は？」「この後は？」）
    ↓
AIが深掘り回答（変化比較・方針提示）
    ↓
ユーザーの理解が深まる
```

入力→解説→質問→深掘り。このサイクルが核。

## 5. MVP機能（Day 1〜2 スコープ）

### Must（これがないとMVPではない）

| # | 機能 | 詳細 |
|---|------|------|
| M1 | 局面解説エンジン | SFEN/KIF入力 → 局面の状況・形勢・方針を自然言語で出力 |
| M2 | 手の理由説明 | 特定の指し手について「なぜその手か」を説明 |
| M3 | 対話型Q&A | 解説に対する追加質問に答える |
| M4 | チャットUI | テキスト入力 → 解説表示の最小限のインターフェース |
| M5 | 解説プロンプト | 将棋解説に特化したシステムプロンプト（これが知的資産） |

### Should（Day 2終了時に余力があれば入れる）

| # | 機能 | 詳細 |
|---|------|------|
| S1 | 変化の比較 | 「A手の場合 vs B手の場合」を対比して解説 |
| S2 | 局面図描画 | SFEN → 将棋盤のビジュアル表示 |
| S3 | サンプル棋譜 | デモ用に5局分の棋譜を事前準備 |
| S4 | レベル切替 | 初心者/中級者で解説の粒度を変更 |

### Won't（MVP対象外）

- 対局機能
- 将棋エンジン統合（やねうら王等のリアルタイム探索）
- ユーザー認証・データ永続化
- 画像OCR / URL自動取得
- 課金
- **中級者向け解説**（MVP後に対応）
- **棋譜の自動インポート**（URL指定、API連携等）
- **棋譜の永続化・履歴管理**

## Web公開前提

このプロダクトはローカル実験用ではなく、**将来的な一般公開を見据えたWebアプリケーション**として設計する。

### 設計の前提
- ブラウザベースのUIとサーバーサイドAPIの分離を前提とする
- API Key（Claude API等）は**絶対にクライアントに露出しない**（サーバーサイドのみ）
- 認証は後回し（anonymous first）だが、後から追加できる構造にする
- ログ・分析・プライバシーは将来対応を意識した設計にする（MVP時点では実装しない）

### MVP時点で守ること
- Next.js API Routes をサーバーサイド境界とし、Claude API呼び出しはサーバー側のみ
- 環境変数で機密情報を管理（`.env.local`、Vercel環境変数）
- CORS/CSP等のセキュリティヘッダーは Vercel + Next.js のデフォルトに任せる
- フロントエンドは公開URLでアクセスされる前提でコードを書く

### MVP後に対応するもの
- ユーザー認証（OAuth / メール等）
- 利用制限（レートリミット、日次上限）
- アクセスログ・利用分析
- プライバシーポリシー・利用規約
- カスタムドメイン

## 8. 成功指標

| 指標 | 目標値 | 計測方法 |
|------|--------|----------|
| MVP完成 | Day 2終了時に品質ゲート通過 | 人間判定 |
| 解説の正確性 | 正確性スコア3.0以上（2以下は不合格） | エンジンデータ照合 |
| 解説の分かりやすさ | 3軸すべて3.0以上、総合3.5目標 | reviewer評価 |
| 追加質問への応答品質 | 質問に的確に答えている率80%以上 | 人間レビュー |
| 1セッション対話数 | 平均3ターン以上 | ログ |

**最重要指標: 解説の品質。** UIの洗練度やデータ量ではない。
解説品質の定義は `docs/explanation-quality.md` を参照。

## 11. 技術選定

| レイヤー | 選定 | 理由 |

| フロントエンド | Next.js (App Router) | Web即公開、Vercelデプロイ |

## 12. 開発体制: 5セッション並列開発

独立した5つのClaude Code CLIセッションが並列稼働する。
subagentの疑似分担ではなく、真の並列セッション構成。

| Role | 責務 | 作業場所 |
|------|------|----------|
| orchestrator | タスク分解・優先順位付け・進捗管理 | main |
| researcher | 将棋知識収集・データ取得・エンジン事前計算 | worktree (research/*) |
| builder | コード実装・プロンプト設計 | worktree (feat/*) |
| reviewer | コードレビュー・品質検証 | worktree (review/*) |
| context-manager | ドキュメント更新・決定記録 | main |

- ハンドオフはdocsとPRコメントで行う
- 正確性レビューはエンジン事前計算データを根拠にする
- **人間だけがmerge/採択を決める**
- 詳細: `docs/review-loop.md`, `docs/context-system.md`, `docs/architecture-principles.md`
