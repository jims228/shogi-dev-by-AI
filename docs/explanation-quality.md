> ステータス: **人間承認済み**（合格ライン・MVPターゲット確定: 2026-03-23）
> 作成: researcher セッション → 人間判断反映
> 根拠: DEC-004, DEC-005, DEC-006, DEC-007

## 1. この文書の目的

「わかりやすい将棋解説」とは何かを定義する。
builder がプロンプトを設計するとき、reviewer が品質を採点するとき、
この文書が共通の判断基準になる。

---

## 2. 前提: このプロダクトの解説は何が特殊か

一般的な将棋解説（テレビ、棋書、YouTube）とこのプロダクトの解説は前提が異なる。

| 観点 | 一般的な解説 | このプロダクト |
|------|------------|--------------|
| 対象局面 | プロの名局・話題の対局 | **ユーザー本人の過去棋譜** |
| 聞き手の前提知識 | 不特定（有段者想定が多い） | **初心者（ウォーズ5級〜3級）** ※MVP |
| 目的 | 鑑賞・エンタメ | **学習（自分の対局を理解する）** |
| 根拠 | 解説者の棋力・経験 | **エンジン評価値 + LLMの言語化** |
| 検証手段 | なし（信じるしかない） | **盤面上で確認可能な説明** |

**事実**: ユーザーの過去棋譜が主な入力であるため、解説は「その人のその局面」に固有でなければならない。
**解釈**: 汎用的な定跡解説や一般論では価値が低い。局面固有の具体的な説明が求められる。

---

## 3. わかりやすい解説の条件

### 3.1 必須条件（これを満たさないと「解説」として成立しない）

1. **将棋の事実として正しい**
   - 駒の位置、手番、利きの関係を間違えていない
   - エンジン評価と矛盾する主張をしていない（例: 悪手を好手と言う）
   - 存在しない手を提示していない

2. **局面固有である**
   - この局面で何が起きているかを説明している
   - どの局面にも当てはまる一般論ではない
   - 盤面の具体的な駒配置に言及している

3. **「なぜ」が含まれている**
   - 手の意味・狙いが説明されている
   - 結論だけでなく、その根拠が示されている
   - 「▲7六歩は好手です」だけでは不十分。「なぜ好手なのか」が必要

### 3.2 品質条件（満たすほど解説が良くなる）

4. **段階的に説明している**
   - 結論→理由→具体例の順で構成されている
   - 1文に複数の概念を詰め込んでいない
   - 読み手が「ついていける」ペースで展開している

5. **専門用語に配慮している**
   - 初心者向け: 専門用語を使う場合は必ず補足説明がある
   - 中級者向け: 基本用語はそのまま使い、高度な用語に補足がある
   - いずれの場合も、用語を使うこと自体が目的になっていない

6. **次の行動につながる**
   - 「ここからどうすればいいか」の方向性がある
   - ユーザーが自分の対局で活かせる学びがある
   - 抽象的な格言ではなく、この局面での具体的な方針

7. **盤面上で確認可能である**
   - 説明されている内容を、盤面を見て確認できる
   - 「飛車が利いている」と言ったら、実際に利いている
   - 変化手順が示されたら、その手順が合法手である

## 4. 良い解説と悪い解説の違い

### 4.1 悪い解説のパターン

| パターン | 問題点 | 例 |
|---------|--------|-----|
| **一般論の羅列** | 局面固有でない | 「角は斜めに利く強力な駒です」（聞いてない） |
| **結論だけ** | 「なぜ」がない | 「▲5五角が最善手です」（なぜ？） |
| **用語の洪水** | 初心者に伝わらない | 「右四間飛車急戦の定跡形から角交換振り飛車に合流」 |
| **事実の誤り** | 将棋として間違い | 盤面に角がないのに「角を打って」と言う |
| **過剰な比喩** | 将棋の理解に繋がらない | 「これはサッカーで言うとオフサイドトラップ」（将棋の話をして） |
| **冗長** | 核心が埋もれる | 前置きが長く、要点が3段落目まで出てこない |
| **盤面と不整合** | 確認できない | 「3三に銀がいるので」（実際には3三は歩） |

### 4.2 良い解説の構造（概念レベル）

良い解説は以下の構造を持つ。（具体的なプロンプト文面はbuilderの責務）

```
[1] 今の状況の要約（1〜2文）
    → 「先手が攻め、後手が受けている局面です」レベルの全体像

[2] この手の意味（2〜3文）
    → なぜこの手が指されたか、何を狙っているか
    → エンジン評価がある場合はそれに基づく根拠

[3] 他の手との比較（任意、1〜2文）
    → 「代わりに○○だと△△になるので、この手の方が良い」
    → 比較することで「なぜこの手なのか」がより明確になる

[4] この局面のポイント（1文）
    → ユーザーが覚えるべき学びを1つに絞る
    → 「このような局面では○○を意識すると良い」
```

**注意**: これは概念的な構造であり、毎回この形式に従う必要はない。
質問への回答、変化の比較、局面全体の解説など、文脈によって構造は変わる。

## 5. 初心者向け解説の条件

### 5.1 想定する初心者像

- 駒の動かし方は知っている
- 基本的なルール（成り、打ち、王手）は知っている
- 戦型名（矢倉、振り飛車等）は聞いたことがある程度
- 将棋ウォーズ 5級〜3級 程度
- 「なぜ負けたのか」「どこが悪かったのか」を知りたい

### 5.2 初心者向け解説のルール

| ルール | 内容 | 理由 |
|--------|------|------|
| 専門用語に補足を付ける | 「飛車先（飛車の前の歩が進む筋）」 | 用語を知らない可能性がある |
| 手順は最大3手先まで | 5手以上の読みは混乱する | 短期記憶の限界 |
| 比喩は将棋の文脈で使う | 「壁を作って王様を守る」はOK、「サッカーのDF」はNG | 将棋理解に繋がる比喩に限定 |
| 1つの説明に1つの概念 | 複数の概念を混ぜない | 情報過多を防ぐ |
| 良い/悪いを明示する | 「この手は良い手です。なぜなら〜」 | 初心者は良し悪しの判断基準を持っていない |
| 盤面の具体的な位置を示す | 「5五の地点に」ではなく「盤の中央に」も併記 | 座標だけでは位置がピンと来ない |

### 5.3 初心者向けで避けるべきこと

- 定跡名だけで説明を済ませる（「矢倉の定跡手順です」→ 定跡を知らない）
- 複数の変化を並列に提示する（混乱する）
- 「当然の手」「自然な手」という表現（初心者には当然ではない）
- 詰みの手順を長く列挙する（3手詰めまでが限界）

## 6. 中級者向け解説の条件（MVP対象外 — MVP後に対応）

### 6.1 想定する中級者像

- 基本的な戦型を知っている（矢倉、振り飛車、角換わり等）
- 手筋をある程度知っている（割り打ち、両取り、田楽刺し等）
- 将棋ウォーズ 1級〜2段 程度
- 「自分の構想のどこが間違っていたか」を知りたい
- 変化の比較ができると嬉しい

### 6.2 中級者向け解説のルール

| ルール | 内容 | 理由 |
|--------|------|------|
| 基本用語はそのまま使う | 「飛車先の歩交換」は補足不要 | 知っている前提 |
| 手順は5〜7手先まで可 | 主要な変化を手順で示す | 読む力がある |
| 変化の比較を積極的に | 「A手だと○○、B手だと△△」 | 比較で理解が深まるレベル |
| 構想レベルの説明を含む | 「この戦型では○○を目指す」 | 個別の手より大局観を求めている |
| 高度な用語には補足 | 「千日手模様（同じ手順が繰り返される状態）」 | 全用語を知っているわけではない |

## 7. 解説品質の評価軸

### 7.1 3軸評価

requirements.md および architecture-principles.md で定義された3軸を、
具体的な採点基準に落とし込む。

#### 軸1: 正確性（Accuracy）

> 将棋の事実として正しいか

| スコア | 基準 |
|--------|------|
| 5 | 将棋の事実として完全に正しい。エンジン評価との矛盾もない |
| 4 | 概ね正しい。細かいニュアンスの違いはあるが、事実の誤りはない |
| 3 | 大筋は正しいが、一部に不正確な記述がある（利きの見落とし等） |
| 2 | 主要な主張に事実の誤りがある |
| 1 | 根本的に間違っている（手番の誤り、存在しない手の提示等） |

**検証方法**:
- エンジンの事前計算データ（評価値・最善手・候補手）との突合
- 盤面状態（駒の位置、利き）との整合チェック
- 人間による最終確認

**注意**: LLMが別のLLMの出力を「正しい」と判定するだけでは不十分。
客観的な根拠（エンジンデータ、盤面事実）が必要。

#### 軸2: 分かりやすさ（Clarity）

> ターゲットユーザーが読んで理解できるか

| スコア | 基準 |
|--------|------|
| 5 | ターゲット棋力の読者がスムーズに理解できる。補足も適切 |
| 4 | 概ね理解できる。一部に補足があるとより良い箇所がある |
| 3 | 努力すれば理解できるが、情報の整理や用語の補足が不足 |
| 2 | ターゲット棋力では理解が困難。用語・概念が高度すぎる |
| 1 | 内容を追うことができない。構成が破綻しているか、前提知識を過度に要求 |

**検証方法**:
- 初心者向け: 「駒の動きとルールだけ知っている人」が読んで理解できるか
- 中級者向け: 「基本戦型と手筋を知っている人」が読んで理解できるか
- 理想的には実際のターゲットユーザーによるフィードバック（MVP後）

#### 軸3: 具体性（Specificity）

> この局面固有の解説になっているか

| スコア | 基準 |
|--------|------|
| 5 | この局面でしか成立しない、完全に固有の解説。盤面の具体的な配置に言及 |
| 4 | 局面に即した具体的な解説。一部に一般論が混じるが中心は固有の説明 |
| 3 | 局面に関連はしているが、似た局面にも当てはまる説明が多い |
| 2 | ほぼ一般論。戦型名を変えれば別の局面にも使える |
| 1 | 完全に一般論。局面を見なくても書ける内容 |

**検証方法**:
- 同じ解説文を別の局面に適用しても成立するか? → 成立するなら具体性が低い
- 盤面の具体的な駒配置・利きへの言及があるか
- エンジンの候補手データに基づいた比較がされているか

### 7.2 合格ライン（人間確定: 2026-03-23）

| 条件 | 基準 |
|------|------|
| **出荷可の最低条件** | 3軸すべて **3.0/5** 以上 |
| **目標品質** | 3軸の総合平均 **3.5/5** 以上 |
| **即不合格ルール** | 正確性が **2.0以下** → 他軸の点数に関係なく不合格 |

**理由**: 分かりやすくても間違っている解説は、学習用途では有害。
正確性だけは最低ラインを厳格にする。

### 7.3 補足: 3軸以外に将来検討すべき評価観点

以下は MVP では評価軸に含めないが、将来的に重要になりうる観点。

| 観点 | 内容 | MVP で含めない理由 |
|------|------|-------------------|
| 教育的有効性 | 読んだ後にユーザーの棋力が向上するか | 測定に時間がかかる |
| 一貫性 | 同じ局面に対して毎回同程度の品質を出せるか | LLMの出力のばらつきは別問題 |
| 適応性 | ユーザーのレベルに合った説明になっているか | レベル切替がShouldレベル |
| 対話品質 | 追加質問への回答が文脈を踏まえているか | 対話のテストは複雑 |

## 8. 評価用局面の収集方針

### 8.1 前提

- ユーザーの過去棋譜が主な入力
- 評価用局面は「典型的にユーザーが解説を求める場面」をカバーすべき
- エンジンの事前計算データ（評価値・最善手・候補手）を付与する

### 8.2 カバーすべき局面カテゴリ

| カテゴリ | 説明 | 選定理由 |
|---------|------|---------|
| **序盤の岐路** | 戦型が分岐する局面（例: 居飛車 vs 振り飛車の選択） | 「なぜこの戦型を選んだの？」という質問が想定される |
| **中盤の攻防開始点** | 駒がぶつかり始める局面 | 「ここからどう攻めればいいの？」が最も多い疑問 |
| **形勢が動いた局面** | 評価値が大きく変動した手の前後 | 「なぜここで悪くなったの？」が学習の核心 |
| **悪手/疑問手の局面** | ユーザーが間違えた手（よくあるミスパターン） | 自分の対局の振り返りが主目的 |
| **終盤の寄せ** | 詰み/必至が見える局面 | 「どう寄せればよかったの？」 |
| **難しい受けの局面** | 攻められている側の最善対応 | 「受け方が分からない」は初心者の典型的な悩み |

### 8.3 各カテゴリで必要な局面数（MVP）

| カテゴリ | 局面数 | 合計 |
|---------|--------|------|
| 序盤の岐路 | 2 | |
| 中盤の攻防開始点 | 3 | |
| 形勢が動いた局面 | 3 | |
| 悪手/疑問手 | 3 | |
| 終盤の寄せ | 2 | |
| 難しい受け | 2 | |
| **合計** | | **15局面** |

### 8.4 各局面に付与するデータ

```
必須:
  - id: 一意識別子
  - category: 上記カテゴリ
  - description: この局面の説明（日本語）
  - sfen: 局面のSFEN文字列
  - move_number: 手数
  - phase: 序盤 / 中盤 / 終盤
  - last_move: 直前の指し手
  - engine_eval: エンジン評価値（先手から見た値）
  - engine_bestmove: エンジンの最善手
  - engine_candidates: 候補手3つ以上（手、評価値）
  - expected_explanation_points: この局面の解説に含まれるべきポイント（リスト）

あると良い:
  - game_context: 対局の流れ（この局面に至るまでの概要）
  - common_mistake: この局面でよくある間違い
  - learning_point: この局面から学べること
```

### 8.5 局面の出典

| 出典 | 用途 | 備考 |
|------|------|------|
| Floodgate棋譜 | 中盤・終盤の局面 | コンピュータ同士だが局面の質は高い |
| 自作局面 | 特定の教育的シナリオ | 著作権問題なし、意図的に設計できる |
| 将棋DB2 | プロの実戦局面（非商用） | 序盤の岐路に適切な局面が多い |

**未決事項**: ユーザーの過去棋譜が主な入力だが、評価用局面にユーザー棋譜を使う場合の取り扱い（プライバシー、再現性）は別途整理が必要。

### 8.6 エンジンデータの取得方法

**未決事項**: MVPでエンジン（やねうら王等）を実行してデータを取得するか、
それとも既存のWeb上のエンジン解析結果（将棋DB2等）を参考にするかは未決定。

選択肢:
- A案: ローカルにやねうら王をインストールして事前計算 → 最も正確だが環境構築の工数あり
- B案: Web上のエンジン解析結果を人手で参照 → 工数は小さいがデータ形式の統一が困難
- C案: LLMの将棋知識で候補手を推定 → 正確性に不安。researcherの責務的に避けるべき

**仮説**: A案が望ましいが、5日MVPではB案で始めてA案に移行するのが現実的か。
→ 人間の判断を仰ぐ。

## 9. 「正しさ」と「分かりやすさ」の関係

この2つは独立した軸だが、時に相反する。

| ケース | 正確性 | 分かりやすさ | どうすべきか |
|--------|--------|------------|------------|
| 正確だが難解 | 高 | 低 | 噛み砕く。ただし正確性を落とさない |
| 分かりやすいが不正確 | 低 | 高 | **不採用**。間違った知識を植え付ける |
| 正確で分かりやすい | 高 | 高 | 理想。これを目指す |
| やや不正確だが概ね合っている | 中 | 高 | 許容範囲だが改善すべき。学習用途では「概ね」は危険 |

**原則: 正確性と分かりやすさが相反する場合、正確性を優先する。**

理由: このプロダクトは学習用途。間違った理解を植え付けることは、
理解できないことよりも有害。「分からなかった」は再質問で解決できるが、
「間違って覚えた」は後から修正が困難。
