# Day 3: plan-only prompt 移行の評価基準

> 担当: reviewer
> 日付: 2026-03-24
> 前提: DEC-014（v2を将棋学習エンジンとして再定義）
> 目的: 現行 buildUserMessage() → plan-only prompt 移行時の品質比較基準を定義

---

## 1. 現行アーキテクチャ vs plan-only の違い

### 現行（v1 prompt）

```
SFEN → parseSfen() → buildUserMessage()
  → [盤面テキスト + エンジンデータ + 玉位置]
  → Gemini が分析 AND 言語化
  → 解説テキスト
```

LLM が担う役割: **盤面の読み取り + 分析 + 言語化** の全工程

### plan-only（DEC-014 方針）

```
SFEN → Canonicalize → Planner（コード側で構造化分析）
  → ExplanationPlan（中間表現）
  → Gemini は Plan を言語化するだけ（Verbalizer）
  → Verifier で検証
  → 解説テキスト
```

LLM が担う役割: **言語化のみ**（分析はコード/エンジンデータが担う）

### 本質的な違い

| 観点 | 現行 | plan-only |
|------|------|-----------|
| LLM に盤面テキストを渡すか | はい | 最小限（または不要） |
| LLM が駒位置を読み取るか | はい（失敗リスクあり） | いいえ（Planner が事前処理） |
| 解説の構造を LLM が決めるか | はい（プロンプトで誘導） | いいえ（Plan が構造を規定） |
| 将棋事実の正確性の担保 | LLM + エンジンデータのヒント | **Plan の事前検証**（LLM に依存しない） |

## 2. テスト基準

### 2.1 比較テストの方法

同じ5局面（pos-001〜005）に対して:
- **A群**: 現行 `buildUserMessage()` でGemini出力（v3の結果を baseline とする）
- **B群**: plan-only prompt でGemini出力

同じ3軸（正確性/分かりやすさ/具体性）で採点し、A群 vs B群を比較。

### 2.2 合格条件（plan-only が現行を置き換えてよい条件）

| 条件 | 基準 | 理由 |
|------|------|------|
| **必須**: 正確性が低下しない | B群平均 ≥ A群平均（3.8） | plan-only の最大の狙いは正確性向上。低下は許されない |
| **必須**: 3軸すべて3.5以上を維持 | B群が C判定条件を維持 | 品質ゲートの後退は許されない |
| **期待**: 正確性が向上する | B群正確性 > A群正確性 | Plan で事前検証するなら、LLM の盤面誤認が消えるはず |
| **許容**: 分かりやすさが微減 | B群 ≥ A群 - 0.4 | Plan の構造に従うことで、自然な文章力がやや落ちる可能性。0.4 以内なら許容 |
| **監視**: 具体性が変化する | 方向を記録 | Plan が具体的な内容を規定するため、向上が期待されるが逆に定型的になるリスクも |

### 2.3 局面ごとの注目ポイント

| 局面 | v3 スコア | plan-only で特に注目すべき点 |
|------|----------|--------------------------|
| pos-001 (序盤) | 正4/分5/具4 | 序盤の方針選択を Plan がどう構造化するか。「3候補とも悪くない」をどう表現するか |
| pos-002 (中盤) | 正4/分4/具3 | ▲7一角打が v3 で省略された。Plan に含めれば具体性が向上するはず |
| pos-003 (終盤) | 正4/分4/具4 | 詰み手順の正確性。Plan に pv_ja を含めれば Verbalizer は手順を間違えないはず |
| pos-004 (四間飛車) | 正3/分4/具4 | v3 で角の位置を「2八」と誤認。Plan に駒位置を含めれば解消するはず |
| pos-005 (終盤寄せ) | 正4/分4/具4 | 「駒得 < 大駒の活用」の教育的ポイントを Plan がどう含むか |

## 3. 5局面別: plan-only で期待される改善とリスク

### pos-001（序盤: 角道を開け合った直後）

**v3 の残課題**: 評価値+127 を「わずかに有利」と表現（ガイドライン上は「少し有利」）。「駒を展開する段階」概念が未言及。

**改善が期待される点**:
- Plan に `eval_expression: "少し先手が有利"` を含めれば、評価値表現の揺れがなくなる
- Plan に `teaching_point: "序盤は駒を展開する段階"` を含めれば、確実に言及される
- 3候補手の比較構造を Plan が規定するため、▲3八銀への評価が明確になる

**悪化しうるリスク**:
- v3 では「角頭（角の真上の地点）」のような自発的な用語補足が出た。Plan に含めない補足は Verbalizer が省略する可能性
- 序盤の「方針の違い」という定性的な説明が、Plan の構造化では表現しにくい

### pos-002（中盤: 角交換型の持ち駒活用）

**v3 の残課題**: ▲7一角打（+510、bestmove とほぼ同評価）が完全に省略。具体性 3/5。

**改善が期待される点**:
- Plan に候補手3つすべてを含め、▲7一角打の「飛車を直接狙う」狙いを構造化すれば、具体性が 3→4 に向上するはず
- ▲2四歩打 vs ▲7一角打の「攻め方の質的な違い」を Plan で明示すれば、教育的価値が上がる
- 飛車位置（8二）を Plan に含めれば、v1 の「2b に飛車」誤認が構造的に排除される

**悪化しうるリスク**:
- Plan に3候補すべてを入れると、Verbalizer が「比較は最大2手」ルールと矛盾する可能性。Plan 側で候補手の取捨選択ルールが必要
- ▲7一角打の狙い（飛車攻め）を Plan が正しく記述するには、利きの分析ロジックが必要。Planner の実装コストが高い

### pos-003（終盤: 3手詰め）

**v3 の残課題**: common_mistake（▲1二金打）未言及。横/縦の方向表現に軽微な混同。

**改善が期待される点**:
- Plan に `mate_sequence: ["▲5一飛打", "△1二玉", "▲2四桂打"]` を含めれば、手順の正確性が構造的に保証される
- Plan に `common_mistake: { move: "▲1二金打", reason: "金が守られていないため取られる" }` を含めれば、教育的な対比が確実に出力される
- 「逃げ場が塞がっている」利きの列挙を Plan に含めれば、LLM が横/縦を混同するリスクが消える

**悪化しうるリスク**:
- 詰み局面の Plan は比較的単純だが、Plan の構造が固定的すぎると「裸玉の危険性」のような Verbalizer の自発的な教育コメントが消える可能性
- v3 では詰み手順を pv_ja で渡して正確に出力できた。plan-only にしても pv_ja 相当の情報は必要で、追加の改善幅が小さい可能性

### pos-004（四間飛車: 角交換の判断）

**v3 の残課題**: 角の位置を「2八」と誤認（正しくは8八）。正確性 3/5。

**改善が期待される点**:
- **最も改善幅が大きい局面**。Plan に `bestmove_detail: { piece: "角", from: "8八", to: "2二", action: "角で角を取って成る" }` を含めれば、位置誤認が構造的に排除される
- 評価値差 +3206 vs -201 の劇的な差を Plan が明示すれば、「守り≠安全」の教訓がより鮮明に伝わる
- 四間飛車の角活用という戦型固有の知識を Plan の `context` フィールドに含められる

**悪化しうるリスク**:
- Planner が「8八の角が2二の角を対角線で取れる」という利き分析を正しく行う必要がある。この分析ロジックの実装が不正確だと、Plan 自体が間違える
- v3 では「馬（うま）」の括弧付き補足が自然に出た。Plan が構造的すぎると、こうした自然な補足が消える

### pos-005（終盤: 龍の使い方）

**v3 の残課題**: ▲2八龍（守りに引く手）への言及なし。具体性は4/5。

**改善が期待される点**:
- Plan に `comparison: [{ move: "▲3三龍", trade: "銀取り", downside: "龍が狭くなる" }, { move: "▲2八龍", trade: "自陣の安全", downside: "攻め速度低下" }]` を含めれば、3候補の質的比較が構造化される
- 「駒得 < 大駒の活用」という teaching_point を Plan が確実に含める
- v1 で発生した「先手の龍を後手と誤認」は、Plan に `piece_owner: "先手"` を含めれば構造的に排除

**悪化しうるリスク**:
- 3候補とも勝勢帯（+2666〜+2855）で差が小さい。Plan がこの「微差の中での質的な違い」を表現できるかは Planner の設計次第
- 出力の自然さ。v3 では「一見攻めから離れるように見えるが」という対比が自然に出た。Plan → Verbalizer では、こうした導入が定型的になるリスク

## 4. ExplanationPlan の最小スキーマ（reviewer 提案）

reviewer として、Plan が**最低限含むべきフィールド**を提案する。builder が実装する際の参考。

```typescript
interface ExplanationPlan {
  // 1. 局面の状況
  situation: {
    phase: "序盤" | "中盤" | "終盤";
    eval_expression: string;       // "少し先手が有利" 等（ガイドライン準拠）
    sente_state: string;           // "攻めの準備中" "攻めている" 等
    gote_state: string;
  };

  // 2. 最善手の説明
  bestmove: {
    move_ja: string;               // "▲7八金"
    piece: string;                 // "金"
    from?: string;                 // "6九" （打ちの場合は省略）
    to: string;                    // "7八"
    purpose: string;               // "角頭を守りつつ囲いの準備"
    is_drop: boolean;
  };

  // 3. 候補手との比較（0〜2個）
  comparisons: Array<{
    move_ja: string;
    eval_expression: string;       // "ほぼ互角に戻る"
    why_worse: string;             // "方針が定まらず展開が遅れる"
  }>;

  // 4. 教育ポイント
  teaching_point: string;          // "序盤は玉を安全にする準備が大切"

  // 5. 詰み手順（mate の場合のみ）
  mate_sequence?: string[];        // ["▲5一飛打", "△1二玉", "▲2四桂打"]

  // 6. よくある間違い（あれば）
  common_mistake?: {
    move_ja: string;
    why_bad: string;
  };
}
```

## 5. 採点時の追加観点（plan-only 固有）

v3 までの3軸に加え、plan-only 移行時に追加で確認すべき観点:

| 観点 | 内容 | 測定方法 |
|------|------|---------|
| **Plan の忠実度** | Verbalizer が Plan の内容をすべて言語化しているか | Plan のフィールドと出力テキストを突合 |
| **Plan に無い情報の扱い** | Verbalizer が Plan にない事実を勝手に追加していないか | Plan → 出力の差分チェック。追加された主張がエンジンデータと矛盾しないか |
| **自然さの低下** | Plan 構造に従うことで文章が定型的になっていないか | v3 の出力と比較して「人間が読んで自然か」を主観評価 |
| **Verifier の効果** | Verifier が不正確な出力を検出・修正できているか | 意図的に不正確な Plan を与えた場合の挙動 |

---

## 6. 移行判定のフロー

```
1. builder が plan-only prompt + Planner を実装
   ↓
2. reviewer が同じ5局面で A群(現行) vs B群(plan-only) を比較テスト
   ↓
3. §2.2 の合格条件を確認:
   - 正確性 ≥ 3.8（現行維持）→ 進む
   - 正確性 < 3.8 → Plan の内容を見直し（LLM の問題ではなく Plan の問題の可能性）
   ↓
4. 人間が最終判定:
   - 移行する → plan-only を本番に適用
   - 移行しない → 現行を維持し、Plan の改善を継続
   - 段階的移行 → 一部の局面タイプ（終盤など）から先行適用
```
