## 3. 根本原因分析

### 原因1（最重大）: USI記法が日本語に変換されずにGeminiに渡されている

**事実**:
- `src/lib/ai/prompt.ts` L76,85 で `engineData.bestmove` と `candidates[].move` をUSI記法のまま出力
- エンジンデータJSONには `move_ja` フィールドがあるが、API型 `EngineCandidate` に含まれず送信されない
- Gemini に渡される実際の入力: `最善手: 6i7h` / `候補手: 1. 6i7h (評価値: +127)`
- GeminiはUSI記法を正しく日本語に変換できない

**検証**: pos-001 で `6i7h`→「▲7七角」、pos-004 で `8h2b+`→「はちいちにびープラス」

### 原因2: Geminiの盤面認識精度が不十分

- pos-002: 後手飛車を8bではなく2bと誤認
- pos-003: 後手玉を1aではなく9aと誤認
- pos-005: 2dの龍を先手ではなく後手の駒と誤認

### 原因3: mate評価値をAPIの number 型で表現できない

pos-003 の `"eval": "mate 3"` をAPIに渡せず、99999で代用。「3手詰み」の正確な表現ができない。

## 5. 今すぐ直すべき点（優先順位順）

### P1: USI記法→日本語変換（最重大・ブロッカー）

**修正方針**: `EngineCandidate` 型に `move_ja?: string` を追加し、`buildUserMessage` で `move_ja` があればそれを使用。エンジンデータJSONには既に `move_ja` が存在する。

### P2: Geminiの盤面認識対策

USI修正後も残る可能性がある。対策案:
- 盤面テキストに「先手玉: X筋Y段目」等の要約を付与
- プロンプトに盤面の読み方ガイダンスを追加

### P3: mate評価値のAPI対応

`eval` を `number | string` にするか、`eval_type: "mate"` フィールドを追加。

### P4: MAX_TOKENS増加

pos-005で出力が途中切断。1024→1536への増加を検討。
