## 5. Verifier の検証

**事実**: route.ts を確認したところ、plan パイプラインでは `buildPlan()` → `buildPlanPrompt()` の流れで Verbalizer に渡しているが、**Verifier による事後検証のステップが API route に組み込まれていない**。

DEC-014 では「軽量 Verifier を必ず入れる」と規定されているが、現在の実装では Verifier はライブラリとして存在するものの、API のストリーミングフローに統合されていない。

**影響**: W2（マイナス値の「帳消し」誤表現）は Verifier があれば検出・修正できた可能性がある。

**提案**: Verifier の統合は次のステップとして実施すべき。ストリーミング出力の後に非同期で検証 → エラー検出時にユーザーに注記を追加する設計が現実的。

## 7. 総合判断

### plan パイプラインへの移行を推薦する

**根拠**:
1. 正確性を維持（4.0）しつつ、分かりやすさ（+0.2）と具体性（+0.2）が向上
2. 駒位置の明示、候補手比較の構造化、用語補足の充実が plan の構造化効果として確認できた
3. 移行判定基準の全条件を達成

**ただし以下の対応を併せて推薦する**:

1. **W1 対応（優先）**: Plan に `mate_sequence` / `pv_ja` を直接含め、Verbalizer が詰み手順を省略しないようにする
2. **W2 対応（優先）**: Plan に各候補手の `eval_expression` を事前計算して含める。Verbalizer の意訳に頼らない
3. **Verifier 統合（次フェーズ）**: DEC-014 の規定通り、API フローに Verifier を統合する
4. **文章長の制御**: Plan の情報量が多い場合に Verbalizer が取捨選択できるよう、priority フィールドを Plan に追加検討

### 最終決定は人間が行う
